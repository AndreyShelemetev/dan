# План разработки «Память рядом»: 10.09.2026 — 10.10.2026

## Как работает этот план
1. Состояние в `main` — единственная правда. Чекбокс задачи меняется только в том же PR, что и её код.
2. `[ ]` — не начата, `[x]` — закрыта. Закрыта = критерий «Готово, когда» выполнен, сборка зелёная, PLAN.md обновлён, PR создан.
3. Идентификатор задачи (например `D07`) стоит первым в заголовке PR и в сообщениях коммитов.
4. Задача занята, если по ней есть невлитая работа: открытый PR с её идентификатором в заголовке, либо не влитая в main ветка `claude/*`, в коммитах которой встречается идентификатор. Занятые задачи не берут и не дублируют.
5. Задачу можно брать, только если все её «Зависит от» уже `[x]` в main, а её внешние предпосылки отмечены.
6. Задача не влезла в сессию: отгружается связная зелёная часть; текст задачи сужается до фактически сделанного и она помечается `[x]` — в уточнённом объёме она действительно закрыта; остаток — новой задачей `<ID>b` сразу после неё (что сделано / что осталось / с чего начать).
7. Красная сборка в PR не уходит. Если main красный ещё до изменений — задачей сессии становится починка сборки вместо плановой.
8. «Журнал» append-only: каждая сессия добавляет одну строку.

Правила разработки — в `CLAUDE.md` (архитектура, слои, PII, деньги, миграции, юрконтур, интерфейсные скиллы). Здесь они не повторяются и не переопределяются.

### Резервные задачи `R1..R4`
Резерв стоит после каждого крупного блока и берётся по общему правилу «первая сверху». Его содержание — не новая функциональность, а хвосты и мелкие долги, которые предыдущие сессии отметили в «Журнале» (недоделанный тест, найденная по дороге неточность в доке, `<ID>b`-остаток, красный флейк). Если долгов нет — сессия помечает резерв `[x]` с пометкой «не потребовался» в том же PR, что и следующая взятая задача, и идёт дальше.

## Верификация в облачной песочнице (замерено kickoff-сессией 10.09.2026, скрипт добавлен D01)
- Стандартная верификация: `dotnet build PamyatRyadom.sln`; во frontend — `npm run build`, `npx tsc --noEmit`, `npm run lint`. Все четыре команды в песочнице проходят зелёными на текущем `main`.
- **.NET SDK не предустановлен.** В песочнице есть только `node` (v22) и `npm` (10.9.7); `dotnet` в PATH отсутствует. Одна команда доводит песочницу до состояния, в котором можно запускать стандартную верификацию:
  ```bash
  bash scripts/verify-setup.sh   # ставит .NET SDK 10 в /opt/dotnet-sdk (если dotnet не в PATH) и делает npm ci во frontend
  export PATH=/opt/dotnet-sdk:$PATH   # только если скрипт ставил SDK
  ```
  Установилась версия 10.0.401, `dotnet build PamyatRyadom.sln` → `Build succeeded, 0 Error(s)` (две предупреждающие `NU1903` про `SSH.NET` 2025.1.0 в тестовом проекте — транзитивная зависимость Testcontainers, не блокирует).
- Во frontend перед проверками нужен `npm ci` (`node_modules` в репозитории нет, установка ~1 мин, делает `scripts/verify-setup.sh`). После него: `npx tsc --noEmit` — без ошибок; `npm run lint` — `✔ No ESLint warnings or errors`; `npm run build` — успешно, 20 маршрутов.
- `dotnet test`: **недоступен из-за Docker.** Демон в песочнице не запущен (`/var/run/docker.sock` отсутствует, клиент `docker` есть, сервер — нет). Замер: `Failed: 135, Passed: 65, Total: 200`; единственная причина всех 135 падений — `DotNet.Testcontainers.Builders.DockerUnavailableException: Docker is either not running or misconfigured`. Проходят ровно те 65 тестов, которым не нужен Postgres (юнит-тесты статусной машины, группировки очереди, опций авторизации, MFA).
  В каждой сессии всё равно пробовать. Недоступность из-за Docker провалом не считать, факт фиксировать в журнале строкой вида «dotnet test: 65/200, остальное DockerUnavailable». Падения по любой другой причине — реальные, их чинит та же сессия.
- `npm run test:e2e` в песочнице **не запускается**: Playwright бьёт по поднятому стеку (`E2E_BASE_URL`, по умолчанию `http://localhost:3100`), а стек — это Docker. Спеки в `frontend/e2e/` уже есть (4 файла), но выполняются они только в CI. Поэтому `D02`/`D03` (CI) стоят в самом начале: без них ни интеграционные тесты, ни e2e не гоняются нигде.

## Вехи (осязаемые результаты в порядке достижения, без дат)
- Сборка, интеграционные тесты и e2e гоняются на каждом PR — то, что песочница проверить не может, проверяет CI.
- Исполнителя и сотрудника можно завести без `DevAccountSeeder`, то есть вне Development.
- Оферта и согласие на обработку ПДн — два разных документа со своими версиями, а не один тип, указывающий на страницу согласия.
- Денежный путь (заявка → смета → принятие → оплата → назначение → отчёт → QA → клиент видит отчёт) покрыт e2e на стабе и зелёный.
- Оплата проходит через YooKassa на конфиге: код готов и зарегистрирован в Production DI, боевой смоук остаётся за человеком.
- Спор — это дело с причиной, разбором и решением, связанное с возвратом, а не только статус `disputed`.
- Клиент, исполнитель и поддержка узнают о событиях письмом, а не по обновлению страницы.
- Боевой стек описан скриптами, конфигами и runbook'ом: развернуть и восстановить можно по документу.
- Документация (`README.md`, `docs/PRODUCT.md`, `CLAUDE.md`, `ARCHITECTURE.md`) совпадает с кодом.
